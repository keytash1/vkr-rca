# Обучаемый RED challenger: сначала новый согласованный transform

20.10.2026. **NO_FIT для прямого переноса старого cache56 в live HTTP.**
Это проверка предпосылки, не новый опыт Accuracy и не дефект объявленного
канонического контракта действующего продукта. Frozen ядро не меняется.

После R3-J есть реальные независимые HTTP-каналы Go и Micrometer. Но обучить
ещё один LambdaMART на имеющемся RE1 cache и сразу применить к этим каналам
некорректно: совпадение имени семейства не гарантирует совпадения признаков.

## Конкретная проверка кода и вычисления

`ml/rca_ml/m9b_features.py::channel_features` выбирает baseline только в
предшествующие600 s и задаёт scale как максимум MAD и
`max(1, abs(baseline_median))*1e-6`. В raw external pipeline единицы разных
источников не преобразуются этим методом в физический HTTP-контракт продукта.

Проверен один и тот же искусственный сигнал:60 baseline points по0,001 s
и20 incident points по0,0015 s, затем те же значения ×1000 (миллисекунды).
Результат старого transform:

| Представление | scale | abs_location_z |
|---|---:|---:|
| Секунды | 0,000001 | 500 |
| Миллисекунды | 0,000001 | 500000 |

Это не scale-invariant на почти постоянном здоровом ряду. Профиль продукта
уже требует канонические единицы — данная проверка не утверждает, что runtime
смешивает секунды и миллисекунды. Она запрещает необоснованно объединить
старый external cache с новым источником для обучения/сравнения.

Во второй проверке те же60 здоровых points отнесены к более раннему отдельному
профильному периоду: метод сообщает baseline_samples0, current_samples20,
available=false из-за фиксированной preceding600s опоры. В рабочем продукте
здоровое состояние намеренно настраивается отдельно и может быть старше.
Нельзя незаметно перенести его timestamps ближе к инциденту ради обхода guard.

Вычисление выполнено существующим research `.venv/bin/python` с `PYTHONPATH=ml`,
без нового пакета, fit, predictions по инцидентам или provider calls. Попытка
использовать минимальное product venv остановилась на отсутствующем pandas;
ничего в продукт ради исследовательской зависимости не устанавливалось.
Raw RE1 metrics.parquet присутствуют локально; это не устраняет необходимость
согласованного определения source kind/statistic и преобразования с нуля.

## Следующий этап, если продолжать исследование ядра

1. Определить версию4-family transform для cpu/memory/error/latency с явными
   unit/statistic/source kind. Не подставлять error counter в error ratio и
   p95 в другой квантиль без объявления семантической разницы.
2. Healthy и incident принимать отдельными интервалами. Проверить шкальную
   инвариантность там, где она заявлена, и физические floors в канонических
   единицах; нулевая активность/дисперсия/пропуск должны различаться.
3. Пересчитать обе стороны из raw по одному transform, а не переименовывать
   старый cache56. Маски/percentiles/aggregates не должны переносить исключённые
   семьи, имена систем, cause labels или ранг frozen модели.
4. До любого fit отдельно зарегистрировать один bounded development-screen,
   а до продвижения — свежий парный набор и критерии. RE1/Go6/Petclinic12 уже
   development; ни старые50, ни эти18 не выдавать за новый скрытый тест.

В текущий продукт не добавляется ещё один недоказанный ранжировщик. Новые
HTTP-факты полезны инженеру уже сейчас; улучшение ML-весов этим не подменяется.
