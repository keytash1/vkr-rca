# R3-G — живой RED-пилот и граница полезности

19.10.2026. **LIVE_INPUT_ACCEPTED; SIMPLE_RRF_NOT_PROMOTED.**
Один проход, шесть из шести воздействий подтверждены, ноль ranker fits и LLM.
Протокол/код/запросы зафиксированы до воздействий и не менялись по исходам.
Рабочие модели, продуктовый репозиторий и DOCX сохранены.

## Что реально выполнено

Предыдущая проверка окружения была неполной: Docker Desktop отсутствует,
но уже установлена Colima с остановленной VM. Существующий профиль запущен
без смены глобального Docker-контекста и перезаписи его конфигурации.
Переиспользованы образы; пересобраны только три собственных Go-сервиса.
Продуктовый контейнер, Petclinic и другие проекты не пересоздавались.

Настоящий Prometheus **2.54.1**, штатный Jaeger **2.20.0**, реальные Go HTTP
и Docker resource exporter. Все три scrape targets доступны. Service label
задан явно для каждого target: не выводится автоматически из имени хоста.
Реальный `promtool check config` прошёл; конфигурация перечитана через SIGHUP.

В новом 70-секундном healthy-интервале: **432** ресурсных точки, **1725** спанов,
нет роста workload failed/dropped. Baseline рассчитан заново только по этому
интервалу. Отдельные request counter, histogram count и +Inf bucket совпали
для каждого сервиса. Временные ряды RPS/5xx ratio/p95 имеют заявленные единицы.
Healthy/RCA/RED окна и сырые API-ответы сохраняются локально в ignored
`artifacts/r3-live-red-v1`, в Git — агрегированные результаты и предсказания.

Каждый случай: 35 s после переключения для очистки 30 s lookback, 35 s
измерение, задержка доставки, потом независимая проверка root HTTP. Так
проверочный запрос не попадает в диагностическое окно. Все воздействия —
либо 200 ms задержки, либо 100% ошибок HTTP у выбранного сервиса.
Нагрузка одна, топология одна; это контролируемый exploratory-пилот,
не новый тест переносимости/Accuracy ВКР.

## Результаты, без отбора удачных случаев

Показана позиция фактического места воздействия; меньше лучше.

| Случай | M13, полученные traces | RED heuristic | M13, traces убраны | RRF, traces убраны |
|---|---:|---:|---:|---:|
| gateway — delay | 1 | 1 | 3 | 2 |
| gateway — error | 3 | 1 | 3 | 3 |
| orders — delay | 1 | 1 | 2 | 2 |
| orders — error | 2 | 2 | 3 | 3 |
| payment — delay | 1 | 3 | 3 | 3 |
| payment — error | 2 | 3 | 2 | 2 |

| Вариант | Top-1, полученные traces | MRR, полученные traces | Top-1, без traces | MRR, без traces |
|---|---:|---:|---:|---:|
| Неизменный M13 | 3/6 | 0,7222 | 0/6 | 0,3889 |
| Resource heuristic | 0/6 | 0,4167 | 0/6 | 0,4167 |
| RED heuristic | 3/6 | 0,6944 | 3/6 | 0,6944 |
| Фиксированный RRF | 3/6 | 0,7222 | 0/6 | 0,4167 |

Два trace-режима — парные представления **тех же шести** случаев, не 12
независимых инцидентов. Удаление traces выполнено в сохранённом входе;
реальный Jaeger в fault-серии не отключался. Контекст baseline один и тот же.

## Вывод по смыслу

1. Независимые HTTP-метрики действительно содержат полезные наблюдения:
   например, local gateway 5xx при прекращении downstream-активности.
   При искусственном отсутствии traces простая RED heuristic оказалась
   информативнее нынешнего M13 **в этом малом проходе**, не вообще во всех системах.
2. При delay на payment симптомы задержки распространяются вверх по цепочке.
   P95 родителей — end-to-end ожидание, а не их локальная работа. Поэтому
   «выбрать самый аномальный latency» ставит gateway выше фактического места
   воздействия. У одинаковых error scores порядок RED может определяться
   tie-break, что не является способностью различать причины.
3. Слепое объединение рангов проблему не решило. Зафиксированный safety gate
   не использовал RED в двух случаях с отсутствием downstream-активности,
   а общий error tie не дал различения в третьем. Смешивать ranks с ошибочно
   нормализованным model score как с вероятностью тоже нельзя.
4. **RRF в продукт не включается.** Один небольшой сигнал не даёт права
   подменять работающий ансамбль или заявлять новую точность. Подбор k/весов
   по этим шести исходам не выполнялся; серия не повторялась.

RRF выбран как простой несупервизируемый контроль, а не как доказанно лучший
метод RCA. Формула и k=60 соответствуют первичной
[работе Cormack et al., SIGIR 2009](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf).
Результаты информационного поиска из этой статьи не переносятся на наш RCA.

## Отрицательные контроли и безопасный вход

После остановки только штатного workload и очистки lookback все сервисы
состояли в `no_activity`: request rate=0, error ratio/p95 undefined.
После остановки только payment scrape получил up=0, и состояние стало
`source_unavailable`, хотя range-query всё ещё возвращал нули request rate.
Контейнер и нагрузчик восстановлены, воздействия сброшены через finally.
После сохранения результатов восемь контейнеров только этого испытательного
проекта остановлены — так же, как до работы. Томов/данных не удаляли.
Рабочий продуктовый контейнер остаётся healthy; глобальный context — default.

Новый экспериментальный `r3_red.py` принимает явные единицы и source coverage,
различает отсутствие запросов, неполный ряд, недоступный/неизвестный источник;
проверяет service scope, диапазон ratio, nonfinite и duplicate series.
Гистограммы суммируются до quantile; готовые p95 реплик не усредняются.
`up` означает успешность scrape, **не здоровье business endpoint**:
[официальная семантика](https://prometheus.io/docs/concepts/jobs_instances/).
Наличие старого rate само по себе не подтверждает свежесть:
[staleness и range queries](https://prometheus.io/docs/prometheus/latest/querying/basics/).
Это исследовательский модуль, он не подключён молча к frozen inference.

## Дополнительный конкретный риск переноса

Проверка старой канонической телеметрии установила:

- все **43784** healthy spans и **128596** spans 120 development-инцидентов
  имеют `span_kind=UNKNOWN`;
- в прежнем cache 1440 candidate rows признаки
  `trace_downstream_wait_ratio_shift` и `downstream_wait_support` всегда нулевые;
- `trace_error_rate_shift` ненулевой только в 24 из 1440 строк;
- `trace_exclusive_median_us_shift` при этом ненулевой в 963 строках:
  `exclusive_duration_us` вычитает ожидания лишь у явных CLIENT descendants,
  поэтому без таких roles это остаток без вычитания ожиданий, не подтверждённое
  локальное время выполнения;
- живые Go-записи имеют SERVER и CLIENT и различают локальный server error
  от failed outbound calls. Это смена наблюдательной семантики, не только имён.

Исторические raw Jaeger responses здесь не сохранились: нельзя объявлять,
что roles потерял именно наш адаптер, а не исходная инструментированность.
В уже выбранном публичном normal SN discovery raw `span.kind` тоже отсутствует,
но это другой capture, не доказательство происхождения каждого старого UNKNOWN.
Аудит не доказывает, что **все** ошибки модели вызваны этой разницей.

## Следующий узкий шаг

Приоритет — проверить переносимый признак **ожидания наблюдаемой зависимости**
по parent/child и временным интервалам, без обязательного SERVER/CLIENT tag.
Это observed-only proxy, не CPU time, не доказанное exclusive time и не
разность p95 (квантили нельзя вычитать как длительности одного вызова).

До нового fit: отдельная регистрация; сначала проверить поддержку такого
сигнала на старых truth-free записях/healthy. Затем один matched контроль
на USED_DEVELOPMENT 120, без новых downloads и grid. Контролировать ширину
матрицы и процедуру; шесть Go-случаев теперь тоже development/диагностика,
не новый hidden test для выбранного по ним улучшения. Если сигнала нет —
остановить эту гипотезу. При положительном результате отдельно валидировать
на свежем подключении/случаях до продвижения в продукт.

RED остаётся основанием для необязательного метрического входа/backup, но
не для немедленной замены весов. На шести близких случаях новый расширенный
LambdaMART не обучать ради положительного числа. Новые UI-функции, LLM-прогоны,
другие корпуса и правки отчёта в этот шаг не добавляются.
