# R3-C: новый корпус — результат проверки совместимости

19.10.2026. **ADAPTER_REQUIRED; NOT_READY_FOR_TRAINING.** Это результат
аудита данных, не оценка точности и не отклонение OpenRCA2 как бенчмарка.
Действующая модель, продукт и оба DOCX сохранены. Новых рейтингов, обучений,
LLM-вызовов и запусков Docker — **0**.

## Что фактически сделано

До загрузки зарегистрирован [протокол](../R3_NEW_CORPUS_PROTOCOL.md).
Из [ops-lite](https://huggingface.co/datasets/anon-ops/ops-lite/tree/581eba39d0bfd2d397eded6cd7cbe3303255521a)
скачаны 30 таблиц трёх выбранных по хэшу discovery-случаев: Hotel Reservation,
OpenTelemetry Demo, TrainTicket. Всего **12 378 083 байта**, 825 007 строк.
Это меньше 12 MiB телеметрии; весь локальный каталог с изолированным PyArrow
занимает около 133 MiB. Полный набор (455 случаев) не скачивался.

Исходные Parquet остались в игнорируемом `external-data/`. В публикацию входят
код, технические агрегаты, схемы и хэши, но не строки телеметрии. Файлы oracle
`env/injection/label/causal_graph` не скачивались. Manifest технически содержит
ответы; из него сохранены только name/system. Названия случаев сами содержат
тип и цель воздействия, поэтому эти три случая — discovery, не скрытый тест.

## Что мешает прямому переносу в наш вход

| Вход | Наблюдение в трёх случаях | Решение |
|---|---|---|
| CPU | `container.cpu.usage`; нет конфликтующих значений при одинаковых сохранённых ключах | Перспективный маппинг в cores после фиксации контракта экспортёра; не смешивать с CPU/node utilization |
| Память | `container.memory.working_set`; нет конфликтующих значений по тем же ключам | Перспективный маппинг в bytes; не подмешивать JVM heap или RSS в тот же ряд |
| Сеть | `k8s.pod.network.io`; нет direction/interface, 7431 группа конфликтующих идентичностей в шести периодах | Не выбирать произвольную строку, не трактовать счётчик как rate; RX для нашего traffic_rate восстановить нельзя |
| Нагрузка | Span-call/request счётчики также имеют коллизии сохранённых ключей; sampling и потерянные измерения не установлены | Не объявлять их полным RPS и не задавать выдуманную нагрузку для baseline |
| Трассы | Есть trace/span/parent IDs, Client/Server/Internal, OTel status, UTC timestamp[ns] | Основа для адаптера есть; duration — uint64 без единицы в схеме/карточке. Не конвертировать молча |
| Сервисы | Метрики включают инфраструктуру/collector/load generator; не каждый кандидат имеет спаны | Нужен явный inventory из архитектуры/профиля; пропавший сервис не удалять |

В нашем старом сборщике `network` — RX+TX bytes/s, `traffic_rate` — RX bytes/s
(`scripts/m13/run.py:46–47`). Назвать оба поля суммой неразличимых значений
нового счётчика означало бы подменить обучавшуюся семантику признаков.

Официальный [контракт kubeletstatsreceiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/kubeletstatsreceiver/metadata.yaml)
задаёт CPU usage в единицах CPU, working set в байтах, а network IO —
накопительным счётчиком с измерениями direction/interface. Это объясняет
возможный механизм потери различий в экспорте. **Не доказывает**, что каждая
версия сборщика корпуса использовала ровно текущий контракт: версия pipeline
и единицы должны быть подтверждены отдельно. Сырые разные значения не являются
«дубликатами для удаления» только потому, что экспорт потерял их измерения.

### Конкретные наблюдения по трассам

| Система | Normal / abnormal спанов | Normal / abnormal сервисов со спанами | Групп повторного trace+span ID в abnormal |
|---|---:|---:|---:|
| Hotel Reservation | 25 475 / 10 607 | 9 / 8 | 59 |
| OTel Demo | 2702 / 2716 | 13 / 13 | 0 |
| TrainTicket | 182 379 / 21 020 | 30 / 29 | 0 |

В Hotel Reservation `geo` виден в normal и отсутствует в abnormal; исключать
его из inventory было бы ошибкой. В TrainTicket аналогично пропал
`ts-cancel-service`, что само по себе не подтверждает причину сбоя.
В OTel Demo есть по 30 нулевых duration в обоих периодах; корректность и смысл
таких записей нужно определить политикой адаптера, не удалять по исходу модели.
В каждом случае встречаются ненулевые parent IDs без родительской записи
в том же периоде. Это может быть граница окна/неполнота, не доказанный дефект.
Счётчик пар Client→Server в JSON включает только однозначно найденных родителей;
он не является полным графом системы или проверенным графом распространения.

Во всех трёх случаях конец normal предшествует началу abnormal. Само название
normal — заявление поставщика, не наша независимая сертификация здоровья.
Границы рассчитаны по наблюдаемым timestamp, без oracle-времени инъекции.

## Независимость и ограничения использования

Сверены trace IDs трёх discovery-случаев с 120 локальными окнами M13 и 50 M14:
**совпадений нет**. Время новых записей — август 2025 и май 2026; старые окна
M13/M14 — сентябрь 2026. Это исключает совпадение обнаруженных trace IDs
с проверенными снимками, но **не устанавливает независимость всех кампаний**
455 случаев или отсутствие пересечения с RCAEval. Остальные случаи остаются
UNASSIGNED: ни train, ни новый закрытый test пока не объявлены.

Карточка набора указывает Apache-2.0, а
[статья, A.6](https://arxiv.org/html/2606.27154v2#A1.SS6) — CC-BY-SA 4.0 для
данных. Поэтому сырые данные и обученные на них продуктовые веса не
перепубликовываются. Пин ревизии обеспечивает повторяемость, не решает лицензию.
Нельзя обучиться на всех случаях и назвать их новым тестом.

## Что делать следующим, без бесконечного перебора

1. **Один контрактный проход по источнику:** найти версию/код полного экспортёра
   с duration unit, direction/interface, temporality, измерениями request count
   и явным service inventory. Не скачивать ещё сотни таких же усечённых таблиц.
2. Если эти поля доступны, зарегистрировать адаптерный пилот на тех же трёх
   discovery-случаях: точные повторения можно схлопывать по объявленной политике,
   конфликтующие значения/циклы — отказ; отсутствующие каналы — masks.
3. Если полный экспорт недоступен, набор оставить для **явно частичного**
   metrics/traces исследования; либо выбрать другой источник с проверенным
   контрактом. Ограниченный перенос не выдаётся за полный.
4. До обучения выделить development и test по кампаниям/системам, запретить
   перенос повторов через границы. Старые M13/M14 не использовать для подбора.
   Discovery-тройка в оценку не возвращается.
5. Только затем — зарегистрированный challenger против matched control,
   frozen champion и простой эвристики. Новые веса продвигаются лишь
   при содержательном выигрыше без неприемлемой регрессии, не по удачному seed.

Это конечный результат текущего аудита. Новый источник найден и практически
проверен, но автоматическое переобучение на нём сейчас дало бы несопоставимый
вход. Продукт не ухудшен ради демонстрации новой цифры.

## Повторение и артефакты

```sh
python -m pip install --only-binary=:all: --no-deps --no-cache-dir \
  --target external-data/r3-openrca2-schema-v1/tooling -r ml/requirements-r3-audit.txt
python scripts/r3_new_corpus_audit.py acquire
PYTHONPATH=external-data/r3-openrca2-schema-v1/tooling python scripts/r3_new_corpus_audit.py schema
PYTHONPATH=external-data/r3-openrca2-schema-v1/tooling python scripts/r3_new_corpus_audit.py semantics
PYTHONPATH=external-data/r3-openrca2-schema-v1/tooling python scripts/r3_new_corpus_audit.py overlap
python -m unittest discover -s scripts -p test_r3_new_corpus_audit.py -v
```

Overlap-stage требует прежние локальные canonical snapshots M13/M14 и seals;
чистый clone не содержит их. Отсутствие останавливает проверку, а не даёт
ложный результат «пересечений нет». Остальные стадии работают независимо.

- [Загрузка: ревизия, размеры, SHA-256](r3-new-corpus-v1/acquisition.json).
- [Схемы 30 таблиц](r3-new-corpus-v1/schema.json).
- [Полные технические агрегаты](r3-new-corpus-v1/semantics.json).
- [Пересечения и неизменность защищённых файлов](r3-new-corpus-v1/overlap-and-protected.json).

Четыре небольшие проверки подтверждают: выбор не зависит от oracle-полей и
порядка manifest, неизвестные системы/небезопасные пути отклоняются, конфликты
не исчезают при подсчёте и лимит загрузки действует даже без Content-Length.
Это проверки инструмента аудита, не доказательство качества ранжировщика.
