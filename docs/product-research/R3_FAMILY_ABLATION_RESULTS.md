# R3-E: полезны ли метрики, которые мы исключили

19.10.2026. **SIGNAL_FOR_FRESH_PILOT**, не выпуск новой модели.
Протокол: [R3_FAMILY_ABLATION_PROTOCOL.md](../R3_FAMILY_ABLATION_PROTOCOL.md).
12 fits завершены за 7,1 секунды; дополнительного подбора не было.
Продукт aea24f5, веса M13 и DOCX сохранены.

## Ответ на вопрос пользователя

Да, в проверенном development-срезе ограничение семейств убирает полезный
сигнал. Дополнительные **метрические задержки и ошибки** заметно помогают
метрическому ранжированию. Сам по себе старый отбор 90→32 не оправдывает
четырёхканальную границу переносимого приложения.

Это не сравнение «нынешний M13 против новой улучшенной версии»: у M13 уже
есть trace latency/error, а здесь сравнивались две одинаковые **metric-only**
модели. Добавочную пользу этих метрик поверх полных traces ещё предстоит
проверить. Сейчас нельзя приписать продукту прирост Accuracy или заменить веса.

## Что сравнивалось

375 известных случаев RE1, 75 групп system/root/fault, три системы. Каждая
система целиком исключалась из обучения соответствующего fold; повторы не
пересекались между train и validation. Источник имеет роль USED_DEVELOPMENT,
не новый скрытый тест. RE2/RE3 и M14 не участвовали в расчётах.

Оба варианта имели одинаковые 56 метрических колонок, кандидатов, глубину,
24 boosting rounds и процедуру. Исключены trace/topology, M11, предварительно
выбранные 32 признака и workload residuals. Последние могли бы косвенно
передавать в узкий вариант сведения исключённых семейств. После маски
пересчитаны aggregate/coverage; метки доступны только обучению и оценке.

Название `restricted_four` означает четыре разрешённых слота старой схемы,
а не четыре реально измеренных канала в каждом случае. По проверенному cache:

| Семейство | Кандидат-строк с наблюдениями |
|---|---:|
| CPU | 7728 |
| Memory | 7729 |
| Traffic/load proxy | 5618 |
| Latency — дополнение | 5372 |
| Error rate — дополнение | 1974 |
| Network, disk и остальные шесть семейств словаря | 0 |

То есть фактическое расширение здесь — **три наблюдаемых семейства → пять**,
а не «четыре → тринадцать». Наличие disk-воздействий в labels не означает
наличия disk IO в признаках. Load proxy не объявляется продуктовым RX bytes/s.

## Результаты на полном знаменателе

| Метрика | Ограниченный вход | Расширенный вход | Разница |
|---|---:|---:|---:|
| AC@1 | 0,6613 | 0,7867 | +0,1253 |
| AC@3 | 0,7920 | 0,9093 | +0,1173 |
| AC@5 | 0,8560 | 0,9653 | +0,1093 |
| MRR | 0,7466 | 0,8587 | +0,1121 |
| Кандидатное покрытие | 1,0000 | 1,0000 | 0 |

Cluster-bootstrap интервал ΔMRR: **[+0,0630; +0,1668]**. Это условный интервал
development-среза, не неопределённость переноса на произвольную новую систему.

| Исключённая из обучения система | MRR узкий | MRR расширенный |
|---|---:|---:|
| Online Boutique | 0,7376 | 0,8728 |
| Sock Shop | 0,9016 | 0,9680 |
| Train Ticket | 0,6007 | 0,7353 |

По типам воздействия наибольший выигрыш у delay (MRR 0,4370→0,7584) и loss
(0,4557→0,6623). Для CPU и disk MRR немного снизился: 0,9549→0,9405 и
0,9467→0,9322. Поэтому вывод не звучит как «стало лучше во всём».

Оба зарегистрированных seed дали одинаковые предсказания: у процедуры нет
stochastic subsampling, поэтому это не две независимые репликации и не
дополнительное доказательство устойчивости. Все исходы сохранены, включая
этот факт. Registered gain/AC@5 gates выполнены; promotion в продукт запрещён
протоколом этого прохода.

## Проверка полного авторского экспорта и другой источник

Из [авторского Zenodo-архива](https://zenodo.org/records/17105974) прочитан
первый datapack, шесть таблиц сохранены локально. Прочитано 13 875 200 байт
сжатого потока; целые 13,4 ГБ не скачивались. Все файлы datapack перечислены
по tar headers: дополнительного raw-варианта в **проверенном datapack** нет.
Схема metrics/sum уже совпадает с усечённой схемой ops-lite: direction/interface
не восстановлены. Это проверка образца, не гарантия одинаковости всего архива.
MD5 всего архива не проверялся; зафиксированы SHA шести извлечённых файлов.

Первичный код формата:
[OperationsPAI/rcabench-platform](https://github.com/OperationsPAI/rcabench-platform/tree/a14339077215690d895305e8898201ca6683cad8),
`src/rcabench_platform/v2/sources/rcabench.py:42–85` выбирает лишь часть Attributes;
`docs/specifications.md:236` прямо задаёт span duration в **наносекундах**.
Предыдущая неопределённость единицы разрешена документацией формата; потерянные
измерения этим не восстанавливаются. Старый протокол R3-C не переписан.

TORAI проверен как альтернатива по официальному RCAEval guide: metadata API
и прямой ndownloader вернули HTTP 403; другой публичный URL — 202 с пустым
ответом на HEAD. Данные не получены. Из документации нельзя заранее заключить,
что это независимые записи, а не обработанное представление RE2.

Следующие конкретные кандидаты по первоисточникам: Eadro (Zenodo 7615394,
небольшие отдельные SN/TT архивы, заявлены cAdvisor RX/TX и latency) и AnoMod
(Zenodo 18342898, новые независимые записи 2026 года; прежде требуется аудит).
Это кандидаты, не уже принятый новый тест. Корпоративные материалы не нужны.

## Решение для следующего шага

1. Проверка полезности расширения метрических сигналов получила основание.
   Не расширять словарь до всех 13 ради количества: фактический сигнал — RED.
2. Найти один подходящий новый срез с происхождением, healthy-периодом,
   inventory, единицами и отдельными request/error/latency наблюдениями.
3. Зарегистрировать matched опыт над нынешним core: дополнительные метрики
   при полных и неполных traces; сравнить с текущими весами и простым fallback.
   Старые 50 случаев M14 не использовать для подбора.
4. Только после этого — версия входного контракта с необязательными семействами
   и возможное переобучение/продвижение. Не менять веса из-за одного dev-результата.
