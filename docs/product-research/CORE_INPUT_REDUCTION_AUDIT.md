## Вывод

**Да, мы сами существенно сузили доступный вход.** Самый важный вопрос для
следующего исследования — ограничение четырьмя метрическими семействами,
а не возвращение максимального количества старых признаков.

| Что сокращалось | Что подтверждено | Оценка |
|---|---|---|
| Исторические вычисленные признаки: 253 → 90 → 32 | Реальные размеры схем M9B/M10C; 32 выбраны по RE1 use/permutation stability с сохранением masks/topology. Сохранён compact gate 90 vs 32: delta AC@1 −0,000458, MRR +0,012732 | Отбор 90→32 имел эмпирическое основание на тогдашней задаче. Эти selection-числа не являются новым независимым подтверждением; сравнение не изолирует переход 253→90 |
| Сырые метрические семейства: 13 в старом словаре → 4 в переносимом адаптере M12 | Остались CPU cores, memory bytes, RX+TX bytes/s и RX bytes/s. Остальные не поддержаны из-за отсутствия обоснованного источника/маппинга в том стенде | Это инженерная граница старого сбора, не результат доказанного отбора четырёх лучших семейств |
| Нынешнее ядро M13 | 59 диагностических + 3 контекстных = 62 признака; собственные trace/error/latency/propagation/disappearance | Не является прежней моделью на 32 признаках. Возврат старых 90 колонок не возвращает потерянную телеметрию |
| Живое подключение продукта | `LiveProfile.load` требует ровно четыре запроса; semantic map и API фиксируют тот же набор | Реальное ограничение расширяемости/переносимости. Новый полезный источник не подключается простым добавлением профиля |

В проверенных протоколах M12/M13 не найдено отдельного сопоставления «те же
наблюдения и та же архитектура: 13 семейств против четырёх». Имеющиеся ablation
metrics/traces отвечают на другой вопрос и используют уже ограниченный вход.
Следовательно, обоснованность прежнего отбора признаков не доказывает
достаточность нынешнего набора исходных сигналов.

## Где именно теряется информация

1. Сборщик стенда и его четыре PromQL-выражения записывают ресурсные метрики.
   Например, disk IO, throttling и признаки очередей не присутствуют в этих
   canonical windows. Их нельзя восстановить очередной обработкой старого файла.
2. `CANONICAL_UNITS` в M12 ограничивает адаптер четырьмя семействами. Старый
   словарь содержит error_rate/latency/disk/saturation/dependency/runtime/
   database/cache/queue; доступность этих семейств здесь нулевая, а не измеренная.
3. Вспомогательный M10C→M11 контекст по-прежнему использует compact 32.
   В его сохранённых деревьях использованы семь признаков. Некоторые из них
   относятся к metric latency/error, которых адаптер не подаёт. Это риск
   переноса старого контекста, а не установленная причина ошибок всего M13.
   Tree gain не доказывает причинность или пользу возвращения признака.
4. Основной M13 получает CPU/memory/network/RX и отдельные trace-сводки.
   Задержки/ошибки уже учитываются из traces. Однако независимые RED-метрики
   могли бы быть полезны при семплировании/потере traces; это требует сравнения.
5. M13 ранжирует всех кандидатов профиля. Старый Top-5 относится к
   вспомогательному reranker, а не к удалению остальных сервисов из итогового
   кандидата. Здесь дополнительное «расширение Top-K» не нужно.

Неполные поля в скачанных ops-lite Parquet — отдельный факт: этот проход
скачивал исходные файлы поставщика с SHA, собственного конвертера до аудита
не было. Наш четырёхканальный контракт и ограничения экспорта внешнего набора
могут существовать одновременно; один не оправдывает другой.

## Следующий минимальный опыт

Цель: проверить пользу расширенного входа **для core и переноса**, не число
новых UI-функций. Сначала подтвердить источник и единицы; потом регистрация
опыта до оценки. Кандидаты по смыслу:

- независимые request rate, error rate и latency из метрик запросов, особенно
  при неполных traces; RPS не называть входящими байтами;
- CPU throttling / disk IO / saturation — только если доступны в выбранном
  источнике и соответствуют проверяемому механизму отказа;
- ослабление обязательности именно четырёх ресурсных семейств — через
  версионированную схему и явную доступность, не заполнение пропусков нулями.

На одних разбиениях сравнить узкий вход, расширенный вход той же модели и
простую эвристику; отдельно при полном и неполном наблюдении. Сохранять
семейства по фактической добавочной пользе. Не увеличивать автоматически
глубину деревьев, число параметров или тип архитектуры. Исторические M13/M14
не становятся новым тестом. Продуктовый inference остаётся прежним до результата.

Загрузка полного авторского архива разрешена пользователем, но пока не начата.
Сначала дочитать код экспортёра и проверить один raw datapack: содержит ли он
нужные измерения/единицы. Если нет — перейти к другому источнику, а не загружать
много тех же непригодных строк. Это часть подготовки опыта, не его конечная цель.
