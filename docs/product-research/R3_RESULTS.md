# R3-A — что получилось

19.10.2026. Исходный опыт: **TECHNICAL_INCONCLUSIVE**. Малый follow-up:
**DESCRIPTIVE_SIGNAL_WITH_FIXTURE_FAILURE**, не новый независимый benchmark.
Отчёт не изменён; веса/признаки/результаты M13 и M14 не изменены.

## 1. Действительное улучшение продукта

Найден и исправлен дефект: изолированный LLM worker отбрасывал операторский
`TIKTOKEN_CACHE_DIR`, в том числе путь к словарю, подготовленному Dockerfile.
При отсутствии словаря использовалась безопасная, но грубая оценка по байтам;
более длинный контекст отклонялся до генерации, хотя короткий вариант проходил.

[PR #3](https://github.com/keytash1/rca-workbench/pull/3): передаётся только
настройка публичного словаря с приоритетом tiktoken / data-gym / default.
Остальное окружение, включая секреты, не наследуется. Проверка SHA словаря,
отсутствие загрузок из worker, лимиты и консервативный fallback сохранены.
В обеих копиях инструкции добавлен явный путь кэша для локальной установки.
146 продуктовых Python-тестов прошли; contracts и Docker image CI зелёные.
Это подтверждает контракт ПО, не эффективность расследования.
PR объединён: main `aea24f51f35790cebe806bb0dc68b9350de83e6e`,
[послесливочный CI](https://github.com/keytash1/rca-workbench/actions/runs/39234728905)
успешен. Локальная продуктовая копия синхронизирована с main.

Локальный vocabulary в первой серии не был прогрет; это отдельная ошибка
подготовки опыта. Её нельзя целиком приписать дефекту Docker-пути. После
отдельного прогрева SHA проверен; все восемь follow-up входов прошли preflight
до первого вызова, с сохранёнными оценками 4496–4790 tokens вместо byte fallback.

## 3. Содержательная оценка follow-up

Разбор выполнен Codex, который знает постановку; это не независимая экспертиза.
Ответы сначала прочитаны с нейтральными answer-ID, затем сверены с регистрацией,
исходными наблюдениями и controller truth. Разбор записан после сверки;
полную слепоту и независимость не заявляем. JSON/reference validation отдельно.

| Случай | Без категорий C0 | С категориями C1 | Вердикт |
|---|---|---|---|
| r3f-01, dependency 403 | Общая гипотеза зависимого вызова; механизм неизвестен | Гипотеза отказа доступа, категория + ошибочные спаны; предлагает проверить коды и место отказа | Есть полезное уточнение механизма, не доказанная первопричина |
| r3f-02, планировался connection refusal | Общая гипотеза зависимого вызова | Корректно сообщает наблюдаемый OPERATION_TIMEOUT | **Сбой постановки воздействия**: фактически TimeoutError, не ConnectionRefusedError; сравнение отказа подключения не состоялось |
| r3f-03, timeout .20 s при client budget .04 s | Общая гипотеза ожидания, не установленный timeout | Таймаут + ожидание; предлагает сверить deadline и принимающую сторону | Есть полезное уточнение; не доказывает, где именно задержка |
| r3f-04, context unavailable при 503 | Общая гипотеза, нужны журналы | Не выдумывает категорию, фиксирует нехватку журналов/исходных спанов | Контроль неполноты пройден: нет «нормального нуля» или уверенной причины |

Заранее заданный знаменатель механизмов — 3: два интерпретируемых C1-only
уточнения, ноль C0-only выигрышей и один **невалидный как запланированный**
случай воздействия. Не выкидываем его для красивого 2/2 или 3/3. Исходный
барьер 14/16 парных ответов не выполнен; серии не складываются в общий успех.

Связь с фактами: PERMISSION_RESPONSE в r3f-01 C1 — obs-001, ошибочные спаны
obs-007; в timeout C1 — obs-001 (категория), obs-007 (timing/errors), obs-002
(наблюдаемая связь). Эти факты поддерживают направление проверки, не вину
зависимости. Для r3f-02 LLM опирается на реально наблюдаемый timeout, не
повторяет скрытое намерение контроллера — это не ошибка LLM.

Все восемь ответов оставляют гипотезы условными; нет выдуманных выполненных
действий/числовой уверенности/установленной причины. Альтернативы сформулированы
как пробелы: локальная ошибка, транспорт, очередь, deadline; отсутствующим
спанам не приписывается отсутствие вызовов. Следующие проверки выполнимы
инженером, но сами не выполнены. action_proposals пусты во всех восьми:
на этих данных конкретные корректирующие/превентивные изменения не обоснованы.

## 4. Критический вывод: что именно помогло

Данные добавили различающий сигнал. Штатный UI уже детерминированно предлагает
для PERMISSION_RESPONSE проверку прав/настроек, для OPERATION_TIMEOUT —
сопоставление бюджета ожидания и задержек. В этих случаях LLM в основном
связывает ту же проверку с графом/наблюдениями и формулирует неизвестное.
**Дополнительное преимущество LLM над этой детерминированной baseline не
доказано.** Нового функционала ради генерации или очередного массового прогона
не требуется. Категории сохраняются необязательным evidence, local-only по
умолчанию; opt-in LLM не заменяет первичные факты и правило UI.

Сборщик ошибся, предполагая, что bound, но не listening socket обязательно
вернёт ECONNREFUSED: на этой машине получен timeout. Это обнаружено при сверке
truth после генераций. В следующем сборе обязательна проверка **фактически
полученного** класса/кода до формирования и отправки пар; даже правильная
команда воздействия ещё не truth. Уже полученные ответы не перезаписываются.

После фиксации исходного runner в исследовательском commit `ba1f8ed` добавлен
`validate_capture`: статусы и класс/код ошибки сверяются до ranking/LLM,
исходный capture сохраняется даже при отклонении. Для отказа соединения порт
закрывается перед запросом; любое неожиданное поведение/повторное занятие
порта отклоняется, а не принимается за задуманный эффект. Четыре локальные
проверки oracle прошли, включая реальные три ConnectionRefusedError на
закрытом loopback-порту. Новых LLM-вызовов после этого нет. Старые ответы и
регистрации остаются неизменными; исправленный сборщик не «чинит» прошлую truth.

## 5. Решения и остаток

- Исправление cache propagation — принять как самостоятельное исправление ПО.
- Сохранить optional categories и строгую неполноту; не менять ML/prompt по
  этим известным случаям, не повторять генерации для успешного процента.
- Остановить этот срез. Никакого нового обучения здесь не проводилось.
- Следующая ML-линия — одна гипотеза + аудит нового train/test корпуса и
  отдельная регистрация по handoff, не оптимизация на 50 известных M14.
- Сравнение LLM без ML-подсказки остаётся отдельным будущим сравнением.
- Отчёт не трогать: V54 SHA-256 по-прежнему
  a12d3063e0e55417603c5fd9c3374090789c217fe2cdcd97c43b0003e8eb176c.

Артефакты: `r3-context-v2/STOPPED.json`, оба registration/data-ledger,
outbound inputs, local captures, responses, masked copies, attempts.jsonl;
`r3-context-followup/preflight.json`. Ничего из аккаунта туда не скопировано.
