# Подключение системы и работа с диагностическим приложением

Это руководство разделяет две роли. Интегратор **один раз** задаёт состав сервисов, доступ к источникам наблюдений и нормальное состояние системы. Инженер при инциденте выбирает систему и интервал в веб-интерфейсе; ему не требуется собирать JSON-файл или знать имена метрик. Результат — полный порядок проверки кандидатов с наблюдениями и покрытием данных, а не автоматически доказанная первопричина.

## Получение и установка

Основной источник продукта — GitHub. Используйте зафиксированную ветку или commit, чтобы код, схема признаков и веса моделей относились к одной версии:

```bash
git clone --branch codex/portable-diagnostics https://github.com/keytash1/vkr-rca.git
cd vkr-rca
python3 -m venv .venv
.venv/bin/python -m pip install -r deploy/product/requirements.txt
```

Для работы нужны Python 3.12+, доступ к профильным API Prometheus и Jaeger и заранее подготовленный здоровый интервал. Раздача исходного кода через GitHub не переносит секреты и не создаёт автоматически профиль нового проекта. Контрольный профиль `lab-system` пригоден только при работающем лабораторном окружении; его наличие в списке не подтверждает доступность источников.

## Что подключается

Приложение читает Prometheus-совместимый API `query_range` и Jaeger-совместимый API поиска трассировок. У наблюдаемой системы должны быть согласованные имена сервисов. Источники и программа диагностики могут работать на разных узлах. Запросы к источникам выполняются на чтение; программа не управляет сервисами и не вносит отказов.

Модель не обучается заново. Общие для всех профилей веса пяти экземпляров LambdaMART и схема признаков проверяются по контрольным суммам. Для каждой новой системы отдельно рассчитывается **неразмеченное здоровое базовое состояние** — ожидаемые величины метрик, трассировочные сигналы и связи. Профиль и базовое состояние задают контекст переноса; точность на конкретной системе проверяют отдельным размеченным испытанием.

## Действия интегратора

1. Скопировать `deploy/profiles/examples/new-system.template.json` под новым именем в `deploy/profiles/`. Шаблон содержит значения `REPLACE_...` и адреса `.invalid`: их необходимо заменить фактическими параметрами. Лабораторный профиль не используйте как основу для другой архитектуры.
2. Задать уникальный `id`, человекочитаемый `title`, версию, **полный отсортированный** список `candidate_services`, путь `artifact_dir` вида `deploy/profiles/artifacts/<id>`. Указать `service_aliases`, если метки в источниках отличаются от имён кандидатов. Сервис без текущей активности всё равно остаётся в перечне.
3. Задать базовые URL источников, метку сервиса в рядах, четыре PromQL-выражения: `cpu` — потреблённые ядра; `memory` — working set в байтах; `network` — **RX+TX**, rate за 5 секунд, байты/с; `traffic_rate` — **RX**, rate за 5 секунд, байты/с. Это определения вычислительного контракта, не произвольные похожие показатели. Выражения возвращают не более одного ряда на кандидата/момент; при репликах сначала применять rate к каждому счётчику, затем суммировать по сервису. Указать `query_step_seconds` (1–60, согласовать со scrape) и `baseline_min_coverage` (по умолчанию 0,8). Для нагрузки выбрать **ровно один** источник: постоянное значение только при обоснованно фиксированной нагрузке либо PromQL-запрос `prometheus_query`.
4. Задать URL Jaeger, `api=jaeger-http-json`, проверенную `tested_version` и дополнительные входные имена в `traces.query_services`. Адаптер также ищет все имена кандидатов/алиасы, объединяет результаты по TraceID и удаляет дубликаты: propagation через один gateway не предполагается. При необходимости токен передаётся через указанную в профиле переменную окружения `token_env`; секреты не хранятся в профиле. Проверить доступность источников с узла приложения; HTTP-редиректы запрещены. Контракт JSON API привязан к проверенной версии Jaeger и не объявляется стабильным публичным API.
5. Выбрать интервал **здоровой работы без меток отказа** и выполнить команду ниже. Она требует метрические семейства для каждого кандидата и наблюдаемые трассировки, формирует два совместимых базовых артефакта и файл происхождения. Существующий каталог она не перезаписывает.

До подготовки базового состояния проверьте доступность и покрытие источников на том же интервале. Команда ничего не записывает и возвращает код `0` только при полных четырёх семействах метрик для каждого кандидата и доступных трассировках:

```bash
PYTHONPATH=ml:cmd/thesis_demo .venv/bin/python cmd/thesis_demo/profile_check.py \
  --root . --profile deploy/profiles/<id>.json --baseline \
  --start 2026-10-16T10:00:00+03:00 --end 2026-10-16T10:15:00+03:00
```

Результат содержит непокрытые семейства по сервисам, долю возвращённых точек относительно шага, число спанов, статус источников и время выполнения. Для здорового состояния нужны наблюдения каждого кандидата, включая спаны: доступность одного gateway не доказывает покрытие остальных сервисов. Проверка контракта не измеряет качество ранжирования. Prometheus lookback может повторять старый отсчёт, поэтому доля возвращённых точек сама по себе не доказывает свежесть scrape; правила свежести учитываются в запросах/настройке источников.

```bash
PYTHONPATH=ml:cmd/thesis_demo .venv/bin/python cmd/thesis_demo/profile_setup.py \
  --root . --profile deploy/profiles/<id>.json \
  --start 2026-10-16T10:00:00+03:00 --end 2026-10-16T10:15:00+03:00
```

Времена в примере заменяются фактическим здоровым интервалом. После установки или изменения профиля приложение перезапускают, чтобы оно заново проверило профиль и артефакты. Для плановой смены базового состояния следует создать версионированный профиль и новый каталог артефактов, проверить их отдельно и затем переключить конфигурацию; удалять действующий каталог во время работы не нужно.

## Действия инженера

Запустить приложение локально и открыть адрес, показанный при старте:

```bash
PYTHONPATH=ml:cmd/thesis_demo .venv/bin/python cmd/thesis_demo/server.py --root .
```

На вкладке анализа выбрать систему и интервал известного инцидента в локальном времени браузера, затем нажать «Рассчитать рейтинг». Интерфейс передаст границы как Unix-время, а ответ покажет их в UTC. Приложение получит метрики и трассировки, построит внутреннее диагностическое окно, рассчитает признаки и вернёт всех кандидатов в порядке проверки. В карточке кандидата нужно изучить наблюдения и полноту данных; гипотезу подтверждают независимо по метрикам, трассировкам и состоянию сервиса. Если метрики недоступны, расчёт отвергается; недоступность трассировок явно показывается в статусе источника и не подменяется измеренным нулём. Запрос ограничен одним часом.

Для сбора задан бюджет 120 секунд, проверяемый между обращениями к источникам; тайм-аут отдельного обращения — 30 секунд. Текущий вызов может выйти за остаток бюджета, поэтому 120 секунд не являются жёсткой гарантией времени ответа. Сводка исходных наблюдений показывает количество, минимум, медиану и максимум по доступным семействам метрик, а также число и ошибки трассировок. Это проверяемые значения источника, а не вклад признака в балл модели. Если часть метрических семейств отсутствует, страница показывает предупреждение о покрытии; рейтинг остаётся гипотезой для проверки. Ответ, у которого отсутствуют обязательные метрики или имеются неоднозначные дубли рядов, отклоняется вместо молчаливого заполнения нулями.

Раздел «Воспроизвести контрольный случай» предназначен для демонстрации и регрессии: он принимает сохранённый пример либо каноническое окно. Это **не** ежедневный пользовательский способ расследования. Раздел независимого испытания показывает опубликованные агрегированные показатели метода и не меняется от выбранного запроса.

## Проверки и границы результата

```bash
PYTHONPATH=ml:cmd/thesis_demo .venv/bin/python -m unittest discover \
  -s cmd/thesis_demo -p 'test_*.py' -v
```

Перед запуском тестов установите `requirements-dev.txt`. Проверки включают HTTP-цепочку с имитаторами, OpenAPI и JSON Schema, ошибки, полный состав кандидатов, изолированные трассы и совпадение всех сохранённых входов в продуктовом и исследовательском расчёте. Фактические подключения и отказы дополнительно проверены на трёх Go-сервисах и внешнем Spring Petclinic; записи находятся в `docs/product-acceptance`. Для своей установки интегратор повторяет E2E и сверяет метки, единицы и данные. Инженерная приёмка не доказывает точность RCA на новом проекте.

Сервер по умолчанию слушает `127.0.0.1`; встроенный HTTP-сервер не содержит учётных записей и TLS. Публиковать его в сети без защищающего reverse proxy и аутентификации нельзя. Конфигурацию источников устанавливает доверенный интегратор; URL нельзя передать через пользовательский запрос. Модели и базовые артефакты доступны приложению только на чтение после подготовки.

## Передача продукта другой команде

После проверки реальных источников и подготовки здорового состояния интегратор может собрать комплект для одного профиля:

```bash
.venv/bin/python deploy/product/build_bundle.py \
  --profile deploy/profiles/<id>.json \
  --output reports/rca-<id>.zip
```

Комплект включает API/UI, вычислительный код, пять итоговых ранжировщиков и необходимые веса контекста базового ранга (один первичный ранжировщик и пять моделей восстановления порядка), профиль и его здоровое состояние. Неиспользуемый Top-3 ансамбль сравнения, разметка, корпус и результаты эксперимента исключены. SHA-256 проверяет все обязательные модельные зависимости, не только пять итоговых файлов. Получатель сначала запускает `python3 verify_bundle.py --root .`, затем устанавливает зависимости и сервер по инструкции архива. Манифест выявляет повреждение, но не подписывает происхождение; общий хеш передают доверенным каналом. Адреса/секреты источников относятся к инфраструктуре получателя. Переносимость исполнения не доказывает точность на новой системе.

Отдельный программный клиент использует [API.md](API.md); машинное описание доступно в запущенном приложении на `/api/openapi.json`. Профили можно хранить отдельно от исследовательских файлов и подключать `--profiles-dir <каталог>`.
