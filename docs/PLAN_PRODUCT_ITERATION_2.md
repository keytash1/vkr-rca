Сначала один ограниченный optional history-context срез, затем единая редакция
полного отчёта: обучение, BARO, навигация листингов и фактический новый контекст.

выявляется только при реально наблюдаемом старте и наличии предыдущего состояния;

Приёмка: один изолированный ограниченный контейнер OOM и SIGKILL, восстановление,
смена лимита и instance ID, последующий исторический запрос; чужие сервисы
исключены. Адресные негативные контракты, неизменность рангов и обычная регрессия.
Не запускать новый benchmark/fit/LLM прогоны. Результаты и ограничения записать.

### Вывод

Четыре ресурсных семейства и трассировки — основа нашей ограниченной задачи
ранжирования сервисов, но не достаточный набор для любого механизма отказа.
Полезные дополнительные наблюдения уже частично реализованы: HTTP RPS/5xx/p95
и ограниченные структурированные журналы/события через Loki. Следующий реальный
пробел — источники исторических событий среды и применённых изменений, а не
ещё один чат или десятки случайных колонок модели.

Разделять улучшение расследования и улучшение Accuracy ядра. Дополнительные
факты не меняют62 признака/веса сами собой. Для learned RED остаётся отдельный
semantic support gate; новые контекстные записи его не обходят.

### Что проверено в нашем продукте

| Уровень | Фактический статус | Граница |
|---|---|---|
| Четыре семейства ресурсов + traces | Вход действующего frozen core | Нельзя приписывать ему новые HTTP/context признаки |
| HTTP RPS/доля5xx/p95 | Optional `http_observations`, опубликовано/проверено | Наблюдения для инженера/разрешённых инструментов, не новый ML input |
| Структурированные логи Loki | Optional `context`, настоящий Loki-пилот выполнен | Не полнотекстовый универсальный поиск и не все поля логов |
| `restart`, `oom`, `deployment`, `configuration_change` | Категории принимаются из корректно подготовленного потока Loki | Это НЕ готовый Docker/Kubernetes/CI/CD collector; происхождение события должен обеспечить источник |
| Прямые события Docker/Kubernetes, история применённых релизов | Готового end-to-end подключения нет | Не объявлять выполненным по одному enum или искусственной JSON-записи |
| Расширенные ресурсы, DB/очереди, profiling | В текущем общем контракте не реализованы | Подключать предметно при различимом механизме ошибки |

Проверены действующие продуктовые `cmd/thesis_demo/context_source.py`,
`context_catalog.py`, `server.py`, `http_observations.py`, `docs/CONTEXT_PROBE.md`.
Локальный учебный `cmd/telemetry-exporter/main.go` читает Docker stats CPU,
working set и RX/TX; lifecycle events/причины завершения/limits он не собирает.
Основное приложение Docker socket не требует. Помощник при отдельном разрешении
получает лишь категории/количества контекста, не произвольные строки и команды.

Два важных текущих ограничения: context запрашивается за тот же start/end,
поэтому релиз ДО начала инцидента может не попасть; timestamp записи Loki
явно не объявляется проверенным временем исходного события. Следующая версия
должна учесть их, а не просто добавить категорию RELEASE в UI.

### Какие данные приоритетны и почему

| Приоритет | Дополнение | Что позволяет различить | Предпочтительный путь |
|---|---|---|---|
| P1 | История OOM/restart/exit/health/readiness | Сервис пропал из-за завершения, пересоздания, аварии или снятия с трафика | Независимый collector → сохраняемый поток событий → bounded RCA adapter |
| P1 | Применённые deployment/config/feature-flag изменения | Что фактически изменилось перед симптомами | Событие системы развёртывания/конфигурации, не просто новый git commit/прошедший CI |
| P2 | CPU throttling/лимиты; память относительно лимита; disk IO/pressure | Высокое использование ресурса против реального ограничения/ожидания | При наличии — cAdvisor/kube-state-metrics/OTel → существующий Prometheus |
| P2 | Пулы соединений, блокировки БД, backlog/lag очередей, DNS/connection errors | Где именно ожидает зависимый сервис и почему | Проектные экспортёры и структурированные ошибки, без универсального доступа к БД |
| P3 | Профили CPU/аллокаций/GC/блокировок | Какая функция/аллокация создаёт ресурсную проблему внутри уже выбранного сервиса | Необязательный внешний profiler; не обязательная часть каждой установки |
| Сквозное условие | Каталог сервисов/реплик/нод/версий/окружений | Кому принадлежит наблюдение и что связано общей инфраструктурой | Стабильные service/instance IDs, scope и время действия соответствий |

Не все эти сведения — «новые виды сигналов»: события могут быть структурированными
логами, рестарты/ограничения — метриками. Важны смысл, происхождение и доступность
за нужный период, а не число подключённых инструментов. База/нода/DNS могут быть
вне множества сервисов-кандидатов: данные среды нельзя превращать в уверенное
обвинение первого сервиса. Такая гипотеза должна оставаться отдельно от ML-ранга.

### Что подтверждают публичные первоисточники

Проверены20.10.2026; для будущего внедрения закрепить конкретные версии.

- [Google SRE, Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/):
  изменения конфигурации/версий и знание системы помогают проверять гипотезы;
  приведён пример перехода от CPU-симптома к профилированию. Это рекомендация
  об источниках доказательств, не обещание процента RCA/снижения MTTR.
- [Docker events](https://docs.docker.com/reference/cli/docker/system/events/):
  есть oom/restart/die/health_status; ретроспективная выдача ограничена256событиями.
  Для исторического интервала нужен заранее собираемый и сохраняемый поток.
- [Docker exit signal](https://docs.docker.com/reference/cli/docker/container/ls/):
  137 указывает SIGKILL; без отдельного OOM evidence объявлять нехватку памяти нельзя.
- [Kubernetes Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/):
  состояние завершённого контейнера содержит reason/exit code/start/finish;
  CrashLoopBackOff — наблюдаемое состояние backoff, не самостоятельный механизм причины.
- [kube-state-metrics](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/metrics/workload/pod-metrics.md):
  restart counter и readiness можно получать в метрическом контуре.
- [cAdvisor metrics](https://github.com/google/cadvisor/blob/master/docs/storage/prometheus.md):
  CPU throttling и OOM counters дополняют utilisation; доступность конкретной
  метрики зависит от runtime/cgroups/конфигурации, не гарантируется по одному имени.
- [Kubernetes API server](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/):
  event-ttl по умолчанию1h; реальные настройки установки могут отличаться.
- [OTel k8s events receiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/k8seventsreceiver/README.md)
  и [Docker stats receiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/dockerstatsreceiver/README.md):
  есть готовые сборщики; stats не равны историческому lifecycle feed. Их установка
  не отменяет scope/полей/прав и не означает, что мы уже их поддержали/проверили.
- [PostgreSQL monitoring](https://www.postgresql.org/docs/current/monitoring-stats.html):
  wait_event/pg_stat_activity позволяют уточнить ожидания зависимости.
- [Docker daemon access](https://docs.docker.com/engine/security/protect-access/):
  широкие права к daemon опасны; не выдавать socket приложению/LLM. Отдельный
  collector с минимальными доступными правами и изоляцией — предпочтение нашей
  архитектуры, не доказанная «полная безопасность». Mount socket:ro сам по себе
  не является политикой разрешённых API-вызовов.

### Следующая реализация только отдельным ограниченным срезом

Сначала завершить согласованную редакцию отчёта (обучение/BARO/листинги).
После неё — один optional history-context этап; не всё перечисленное сразу.
Это уточняет следующую исследовательскую итерацию, а не создаёт новый долг
принятой ограниченной ВКР. По текущему исследовательскому вопросу код не менять.

До реализации выбрать один настоящий доступный источник, предпочтительно
локальный Docker событийный стенд с сохранением в уже поддержанный Loki;
Kubernetes не разворачивать лишь ради демонстрации широты. Сначала проверить,
какие поля/event clocks сохраняет существующий v1 и где нужна отдельная версия
контракта. Сейчас он отбрасывает произвольные exitCode/containerID/limits;
просто отправить JSON в Loki недостаточно, чтобы они дошли до инженера.

Минимальная приёмка без большого нового корпуса:

1. Истинный OOM ограниченного одноразового учебного контейнера и отдельный
   SIGKILL/restart не смешиваются. Не создавать давление памяти/диска хоста
   пользователя и не трогать чужие контейнеры. Controller labels/fault names
   не являются диагностическим входом.
2. Применённое изменение выбранного сервиса перед инцидентом видно с provenance;
   посторонний релиз не попадает в scope и не объявляется причиной.
3. Исторический запрос после восстановления не подменяется текущим inspect.
   Короткий предшествующий context-lookback явно обозначен отдельно от
   диагностического интервала; прежний input модели не расширяется молча.
4. Дубликаты, задержка доставки, смена instanceID, усечение/отказ/неизвестное
   покрытие различаются. Хранить event/source-observed/fetched времена там,
   где они действительно известны; не придумывать event clock.
5. Факты видны в существующей раскрываемой группе, сохраняются в snapshot;
   LLM получает только отдельно разрешённую фиксированную проекцию.
   Нет нового большого dashboard и обязательного Kubernetes/Docker для RCA.
6. Старые профили/снимки работают, ML features/ranks по тем же входам неизменны.
   Продвижение — по двум различимым механизмам и отрицательным контролям,
   не по фиктивному росту Accuracy. Нужны1короткий проход и адресная регрессия,
   не новая серия50инцидентов/LLM benchmark.

P2/P3 остаются условными направлениями: развивать только по конкретной ошибке,
где источник различает конкурирующие гипотезы. Сотни метрик и обязательный
eBPF/profiling-стек не являются критерием готовности ближайшего выпуска.

**Зачем:** реальный R3-I показал различающие HTTP-ошибки и задержки независимо
от traces, но инженер пока не получает эти ряды в обычной карточке. Предоставить
факты полезно отдельно от недоказанного изменения ML-порядка.

**Граница:** optional профильный блок `http_observations` версии v1 на том же
Prometheus/credential scope. Три запросa: completed requests/s, server 5xx ratio,
histogram p95 seconds, плюс явный per-service source-presence query. Интегратор
один раз задаёт unit/statistic/query, инженер по-прежнему выбирает систему/интервал.
Модель не получает эти поля, её 62 признака/веса/healthy contract не меняются.
Обязательно объявить lookback_seconds: query timestamps лежат в выбранном
интервале, но rate/histogram расчёт первых точек может затрагивать предшествующие
наблюдения. Эту оговорку сохранить в snapshot/UI/числовом контексте помощника.
Профиль без блока делает ровно прежние запросы и даёт прежние model outputs.

**Результат:** ограниченный collector → отдельные observations evidence-каталога
→ сохранённый snapshot/API → одна закрытая по умолчанию HTTP-группа в карточке.
Не новая панель/чат/дашборд. Все значения с единицами/интервалом/источником;
оценки p95 по временным точкам не выдаются за общий p95 всего интервала.
Никакого ручного JSON инженеру, нового endpoint источника или Docker socket.

**Fail-safe и приёмка:**

- Не более четырёх queries, общий wall deadline <=6 s в одноразовом worker,
  byte/point/service budgets, без redirect/retry и source-text ошибок в ответе.
- Missing series, no activity, source unavailable и partial различаются.
  При up=0 старые rate нули не становятся наблюдаемой нормой; error ratio/p95
  без активности не определены. Дубликаты, чужие сервисы, неверные units,
  ratio вне [0,1], отрицательные/nonfinite значения отклоняются/помечаются.
- Failure optional источника сохраняет рейтинг/основные факты. Config входит
  в analysis cache key; old baseline не нужно переобучать ради evidence-only
  полей. Снимок не перечитывает источник при открытии истории.
- LLM видит только существующую разрешённую числовую metric-проекцию. Нет
  исходных labels/URL/ошибок, новых provider вызовов или автоотправки в проверках.
- Одинаковые канонические входы дают точно тот же ML ranking/features hash
  с блоком/без него. Старые профили/снимки/API работают; source failure и
  cache invalidation проверены адресно, UI — один настоящий браузерный проход.
- Семантика проверяется на записанных фактических Go/Micrometer ответах;
  один короткий живой Go-проход для wiring/idle/outage, не новая серия Accuracy.
- Новые runtime модули входят в bundle/export/Docker. Перед merge — один
  полный продуктовый regression и CI, не повтор старых LLM/ML опытов.

## 3. P2-01: применимость базового состояния

Сейчас evidence выдаёт `BASELINE_LOAD_COMPARABILITY_NOT_ESTABLISHED`
для любого случая. Нужны причины, а не выдуманный процент уверенности.

Записывать в provenance здорового состояния использованный моделью RPS
и источник этой величины. Настроенная константа — допущение интегратора,
не измерение фактической нагрузки. Среднее одного интервала не является
диапазоном всех допустимых нагрузок. Нельзя объявлять интерполяцией то,
что модель обучена по одной агрегированной точке.

В evidence оценивать отдельно временной порядок и нагрузочную опору:

- нет новых метаданных → неизвестно, прежние установки продолжают работать;
- здоровый период позже/перекрывает исследуемый → явное предупреждение;
- настроенная, а не измеренная нагрузка → отдельная оговорка;
- текущая агрегированная нагрузка отличается от опорной → указать обе
  величины/отношение, не придумывать универсальный порог допустимости;
- совпадение RPS само по себе не доказывает неизменность конфигурации,
  полноту baseline или корректность модели.

Оценка — надстройка наблюдений, не дополнительный признак ранжировщика.
Сохранённая карточка и инструменты LLM должны видеть ту же оценку. Слепой
режим сравнения не получает скрытый ранг через неё.

## 4. P2-02: дополнительный контекст

Первый исследуемый источник — ограниченный поиск структурированных ошибок
и событий через Loki-совместимый API. Альтернатива — нормализованный поток
изменений CI/CD. Выбор подтвердить после проверки настоящего API и контракта;
не требовать обязательного Loki или Docker у каждой компании.

Контракт: система, сервис, время события, время наблюдения, вид, источник,
ограниченный безопасный набор полей, идентификатор/ссылка и статус покрытия.
Не смешивать timestamp события и время доставки. Пустой ответ, неподключённый
источник, обрыв, усечение лимитом и успешно прочитанный интервал различаются.

Только серверная конфигурация источника и read-only запрос. Ограничить
интервал, число записей, байты и время. Не разрешать модели URL, LogQL,
Docker socket, shell или произвольные поля логов. Не обещать, что regexp
автоматически удалит все секреты: по умолчанию внешняя передача нового
контекста выключена, нужны явные поля и разрешение установки.

Сначала контекст помогает инженеру; модель ранжирования не меняется.
Рядом с событием показывать, что близость по времени не доказывает причинность.
Случай полезности: похожие задержки и ошибки в метриках/трассах, но конкретное
исключение или изменение доступа отличает сетевую проблему от отказа
авторизации. Отрицательный контроль: нерелевантный релиз в соседнем сервисе
не должен автоматически становиться причиной.

Пример с заранее известной причиной — инженерная иллюстрация разрешимости,
не независимый эксперимент точности и не доказательство сокращения MTTR.

## 5. P2-03: направление исследования, а не обязательное новое ядро

Сначала разложить ошибки по механизму: невидимая зависимость, исчезновение
активности, распространение симптома, другой режим нагрузки, недостаток
данных и неоднозначность причины. Отдельно проверить полноту кандидатов.
Для разметки допускается источник вмешательства; в данные диагностике он
не передаётся. В частности, название chaos-сценария/команда инъекции в логе
не должны превращаться в подсказку модели.

Кандидаты на последовательную проверку:

1. Контекст ошибки/изменения против тех же наблюдений без контекста.
2. Проверяемый путь распространения симптома против названия одного сервиса.
3. Дополнительные временные признаки против текущих агрегатов.
4. Более широкий здоровый диапазон нагрузки и контекст против одной опоры.
5. Retrieval похожих **подтверждённых** расследований — сначала только справка.

GNN, новый ранжировщик, калиброванная уверенность, автоматический детектор,
мультиагентная оркестрация и автоисправление не являются задачами по умолчанию.
Для каждого challenger — отдельный протокол до просмотра нового теста.
Переобучать весь зависимый контекст внутри обучающих разбиений; использовать
кластерные разбиения и полный знаменатель. Сравнивать с прежним champion,
метрической эвристикой и простым детерминированным решением того же пробела.

Для LLM нужны одинаковые данные/инструменты и четыре вопроса: верна ли
гипотеза, обоснована ли она фактами, рассмотрена ли альтернатива, полезен ли
следующий проверочный шаг. Совпадение ID ссылки не подтверждает вывод.
Измерять ошибки и затраты, а не только успешный JSON. Пользовательское
ускорение измерять отдельно. У слепого LLM-режима убрать также косвенную
передачу ранга. Старый незавершённый прогон не продолжать задним числом.

Вердикты: PROMOTED / REJECTED / INCONCLUSIVE / NOT_JUSTIFIED. При недостатке
новых независимых данных итог — INCONCLUSIVE, а не «готовая улучшенная модель».
Следующий опыт должен быть небольшим пилотом с заранее ограниченным числом
случаев; расширение — лишь после обнаруженного содержательного сигнала.
