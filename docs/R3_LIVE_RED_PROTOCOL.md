# R3-G: настоящий Prometheus и малый пилот независимых RED

19.10.2026. До новых воздействий, inference и просмотра результатов.
Цель — принять метрический вход и проверить простой способ использовать его
при полном/отсутствующем trace-входе. Не новый тест ВКР, не подбор по M14.
Источник — собственная цепочка gateway→orders→payment, реальные HTTP/контейнеры,
Prometheus 2.54.1 и Jaeger 2.20.0 по уже закреплённым digest.

## Конечный объём

Один проход: здоровые наблюдения ≥70 s; шесть случаев = три места воздействия
× два механизма (200 ms задержка либо 100% server errors). Каждый случай:
35 s прогрев после переключения, 35 s измерение, запрос API после завершения
и задержки доставки. Нагрузка штатного workload 5 requests/s. Предел 15 минут
после запуска контура; никакого автоматического повтора по результату.
Первый healthy не считать успешным без нулевого фактического роста failed/dropped.
Инъекция задаётся только через /debug/fault своих сервисов, сбрасывается finally.

До fault-серии проверяются 3/3 scrape, три RED query, соответствие абсолютных
counter/histogram count/+Inf и здоровое отсутствие 5xx. Проверяется, что
metrics имеют service scope, rate requests/s, error ratio [0,1], histogram
quantile seconds. Это upstream-completed server latency, не локальное время
вычисления сервиса и не доказательство причины.

Все канонические CPU/memory/RX/TX собираются настоящим штатным адаптером.
Baseline здоровой системы рассчитывается заново, не берётся из старой сессии.
Healthy trace sampling/backend limits не выдаются за гарантированную полноту.

## Сравнение до знания исходов

Все кандидаты сохраняются. Два наблюдательных режима каждого случая:
фактически полученные traces; те же resource/RED при traces=[],
traces_collected=false (имитация потери модальности, не физическое отключение).
Baseline один и тот же, новых скрытых меток в признаки нет.

1. Неизменный ансамбль M13 и простая resource metric heuristic.
2. RED heuristic: для каждого сервиса максимум положительного standardized
   отклонения error ratio и p95 от собственного healthy. Масштаб healthy IQR
   с физическим минимумом 0.01 для ratio и 0.001 s для p95. Не сравнивать
   напрямую миллисекунды и долю ошибок. Нет нормального значения при пропуске.
   Центр — healthy median, текущее значение — median точек измеряемого окна.
3. Один фиксированный exploratory challenger: reciprocal-rank fusion M13 и
   RED ranking, k=60, равные веса. Это дешёвый контроль, не обучение нового
   ансамбля. Общий RED tie даёт общий средний rank, а не предпочтение по имени.
   При нулевой/неполной поддержке RED не участвует (остаётся M13).
   Полнота здесь требует положительного request rate и конечных error/p95
   у всех кандидатов; иначе невалидный канал не меняет порядок модели.

35 s прогрева выбраны до первого воздействия: каждый 30 s rate/quantile
в измеряемом окне должен целиком относиться к одному состоянию, с запасом
на 2 s scrape. Не смешивать предыдущий инцидент со следующим.

Формулу/порог не менять по шести исходам. 62 признака и веса M13 не изменяются.
Train-данных независимых RED пока нет; обучать полноценный расширенный M13 на
шести близких случаях нельзя. Этот пилот решает, оправдан ли следующий сбор,
а не пытается заменить его красивой точностью.

## Проверки результата и решение

Сохранить каждый случай до присоединения root metadata; отдельно controller
ledger. Сверить реальный root HTTP-ответ и 5xx/latency изменение с воздействием;
при несоответствии оставить случай невалидным, не менять root/не повторять.
Полный знаменатель шесть; невалидные случаи видны, не удаляются из отчёта.
Показать rank каждого root и AC@1/MRR каждого варианта/режима без CI на 6 cases.
Не считать два режима независимыми случаями.

Если простой challenger не даёт устойчивого добавочного сигнала или вредит
полным traces, его не продвигать. Даже если выигрывает на этом контролируемом
проходе, отдельная свежая проверка нужна до весов/замены продукта: PROMOTION
для этого пилота запрещён. Иметь полезный дополнительный факт и уметь улучшать
порядок кандидатов — разные результаты.

После основной серии один idle-контроль ≥35 s: request rate=0, error ratio
и p95 undefined, не «здоровый ноль». Затем один scoped scrape-outage: up=0,
не нормальная пустая нагрузка. Остановить только контейнер своего стенда и
восстановить его finally; никакого воздействия на продуктовый контейнер,
Petclinic и другие проекты. LLM и DOCX не трогать.
