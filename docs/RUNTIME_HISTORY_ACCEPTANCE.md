# Приёмка исторического контекста 20 октября 2026

Один реальный локальный проход: Docker/Colima → отдельный collector → Loki 3.7.8
→ обычный bounded context adapter. Два одноразовых контейнера, без сети,
с CPU/pids/memory limits; после опыта удалены только их точные ID, томов не было.

В контейнере с лимитом 48 МиБ выделение 128 МиБ вызвало настоящее событие oom,
OOMKilled=true и завершение 137. Затем обычный SIGKILL дал тот же код 137,
но OOMKilled=false и без oom в соответствующем интервале. Это различает два
наблюдаемых механизма остановки, не устанавливает исходную причину роста памяти.

После восстановления, изменения memory limit и замены image/instance прочитаны
11 сохранённых записей. Последующий запрос с lookback 60 с нашёл их как события
до инцидента; без lookback записей в самом коротком интервале не было. Смена
image и memory limit определена из наблюдений start/inspect, не из сценарных
меток. Повторное чтение daemon не создало новых записей outbox. Каталог сохранил
те же идентификаторы входа модели; в отдельной проекции помощника нет container ID.

Адресные проверки охватывают scope, повтор/перезапуск SQLite, поздний start,
диапазон lookback, фиксированные поля, приватность и видимость предупреждений.
Основная регрессия приложения и UI пройдена. Это инженерная приёмка одной
реализации Docker/Loki, не испытание Kubernetes, точности ранжировщика, экономии
времени или полноты исторического покрытия. Весовые файлы не менялись.

Протокол воспроизведения и receipt находятся в материалах проекта
`scripts/accept_runtime_history.py` и `docs/product-research/runtime-history-v1/receipt.json`
репозитория vkr-rca. История до установки collector и после потерь неизвестна;
ретроспективный inspect не используется как доказательство старого состояния.
