# R3-I — метрический резерв: подготовка источника

20.10.2026, до запуска нового стенда и чтения новых fault-данных.
Цель — исправлять конкретную слабость при отсутствии incident traces,
а не добавлять ещё признаки к full-trace модели. DOCX/веса продукта не менять.

## Этап 0: только здоровое подключение независимого приложения

Использовать уже закреплённые официальные образы Spring Petclinic, не новый
архив. Отдельный Compose project `rca-r3-red-petclinic`, без изменения старого
приёмочного проекта и запущенного продукта. Настройки — только измерения:
Micrometer HTTP histogram, отдельный Prometheus scrape, ограниченные actuator
endpoint, низкая учебная нагрузка. Chaos Monkey доступен только loopback и
изначально выключен. Никаких memory/kill/CPU assaults на этом этапе.

Для каждого из четырёх кандидатов проверить настоящий requests count,
5xx numerator, cumulative duration buckets с +Inf, секунды, business-only URI
scope, отсутствие actuator traffic в знаменателе, достаточную healthy
активность. Квантили вычисляются после суммирования buckets по репликам,
не усреднением готовых p95. Gateway может использовать другую instrumentation:
при несовместимой семантике не подменять её молча и не делать fit.

Минимальный положительный gate: 4/4 кандидатов имеют активные HTTP count и
duration histogram, проверяемый denominator и стабильные 200 по трём путям;
есть нормальный ресурсный capture и healthy topology без labels причин.
Предел подготовки 30 минут. При неуспехе сохранить конкретный blocker,
не строить ещё один кластер. Сохранить upstream image digests/config hashes,
сырые ответы локально (ignored), в журнал — лишь агрегаты и схемы.

Далее, до fault-воздействий, отдельная регистрация алгоритма, сравнений,
сценариев, split и бюджетов. Старые Go-6 — только development: по ним нельзя
объявлять независимое качество нового резерва. Простой RRF уже отклонён.
Новый резерв не должен менять full-trace путь или превращать отсутствие
RED/здорoвой опоры в уверенный результат.

## Первичные основания

- [Spring Boot HTTP server metrics](https://docs.spring.io/spring-boot/reference/actuator/metrics.html):
  URI template и статус — измерения, endpoint presence не равно готовым рядам.
- [Micrometer histogram](https://docs.micrometer.io/micrometer/reference/concepts/histogram-quantiles.html):
  aggregable histogram, не client-side quantile average.
- [Chaos Monkey](https://codecentric.github.io/chaos-monkey-spring-boot/latest/):
  официальные bounded latency/exception assaults, reset после каждого случая.
- [MicroRCA](https://ieeexplore.ieee.org/document/9110353/): граф и распространение
  аномалий мотивируют topology-aware сравнение, но не доказывают наш вариант.

Зафиксировать результаты даже при отрицательном gate. До отдельного
сопоставимого результата не объявлять этот этап улучшением Accuracy.

## Этап 1: фиксированный topology-aware RED reserve

Healthy gate пройден: 4/4 scrape, 656 resource samples, 4394 spans,
counter/+Inf равны, фактический рост failed/dropped нулевой. URI UNKNOWN
gateway сохраняется: при известной штатной нагрузке это также business traffic,
actuator исключён отдельно. Разметки новых отказов ещё нет.

До первого отказа фиксируется один простой резерв без обучения. Он ничего
не меняет при доступных incident traces. При их отсутствии требует здоровый
граф и источники всех кандидатов (допустим наблюдаемый idle, не source outage).
Аномалия — положительный shift error/p95 >=3 healthy IQR с прежними физическими
минимумами. У кандидата совместимый downstream symptom, если его прямой callee
аномален по тому же каналу, а абсолютный прирост callee >= половины прироста
caller. Это эвристика совместимости, не разность квантилей и не доказанная
причинность. Сначала кандидаты без такого downstream symptom, затем прочие
аномальные, затем остальные; внутри tier прежний RED score, ties — исходный
ML rank. При нетопологическом/циклическом/неполном входе резерв не применяется.
Граф берётся только из здорового периода, не достраивается по fault traces.

Сравнения: frozen M13, прежняя RED heuristic, reserve; один и тот же candidate
universe и baseline. Полный trace-путь проверяется на точное сохранение порядка.
На Go-6 разрешена только диагностика разработки, не выбор коэффициентов.
Не менять пороги после этой диагностики.

Свежий prospective пилот: Petclinic, три места воздействия (customers, visits,
vets) × два механизма (latency/exception) × две интенсивности. Latency 100/300 ms
на каждый controller call; exception level 2/1 (каждый второй/каждый вызов).
12 случаев, порядок: для интенсивности low/high последовательно каждый сервис,
внутри latency/exception. 35 s очистка после reset/нового воздействия, 35 s
измерение, 5 s доставка. Одно выполнение; невалидные случаи не заменять и не
выбирать удачные интервалы. Сырой capture сохраняется до oracle/меток.
Предел 25 минут после старта. Все assaults сбросить в finally, без kill/memory.

Oracle после capture: 10 прямых запросов target подтверждают задержку или
5xx (для level2 хотя бы один, level1 минимум 8/10); эффект также виден в RED
target (p95 >=0.07/0.24 s либо error ratio >=0.1/0.7). Root metadata не попадает
в ranking API. Все 12 входят в основной знаменатель, valid subset отдельно.

Primary — masked ΔMRR против frozen M13 и против RED-only. Для рассмотрения
интеграции требуются все 12 валидных, ΔMRR >=0.03 и положительная нижняя
кластерная CI для обеих сравнительных линий, AC@3 не хуже, full-trace путь
идентичен, нет скрытой потери кандидатов/аварийного source→zero. Кластер
root×mechanism, интенсивности внутри одной группы; 2000 bootstrap seed20261020.
Малый пилот не доказывает универсальную точность и не меняет M14.
Провал — отрицательный/неопределённый результат, не повод повторять до успеха.
Успех — основание для отдельной ограниченной продуктовой интеграции с явными
условиями применимости и opt-in, не молчаливая подмена научного champion.

### Техническая поправка до первого измеренного fault-случая

Первый runner включил fault-инструмент, но остановился до ожидания/сбора:
сравнил весь status dict с `{enabled:true}`, тогда как официальный endpoint
также возвращает enabledAt/enabledFor. В finally инструмент выключен;
fault-окон/сравнительных Petclinic предсказаний нет. Исходник и регистрация
сохранены. Новый pilot-v2 проверяет сам boolean enabled, не отбрасывает
дополнительные штатные поля. Алгоритм/пороги/12 сценариев не меняются,
fit по-прежнему ноль. Производные healthy baselines переиспользуются лишь
при полном равенстве повторному расчёту. Повторный healthy capture не нужен.

### Возобновление после первого измерения, без повторения случая

p-001 измерен, сохранён и валиден. До второго воздействия API отклонил нулевые
latencyRangeStart/End даже при latencyActive=false. При выключенном инструменте
подтверждено принятие того же exception config с положительными неактивными
границами. Сохраняется исходник до исправления. Продолжить оставшиеся p-002..012
с явной resume-регистрацией и проверкой неизменности p-001/всех входов.
Ни случай, ни healthy не повторяются; формула и критерии прежние.
Для неактивной latency оставить 100/100, latencyActive=false; это не новое
воздействие. Включить deterministic=true: level2 означает каждый второй вызов,
а не случайную вероятность default false. Для уже измеренного level1 различия
нет. Новые exception outcomes до этой поправки отсутствуют.
