# История контейнеров как необязательный контекст

Основной RCA по-прежнему обращается только к Prometheus/Jaeger и при настройке
к Loki. Docker socket не монтируется в приложение или помощник. Отдельный
операторский `tools/docker_context_collector.py` выполняет чтение Docker events
и двух разрешённых полей inspect: image ID и лимит памяти. Доступ к daemon
остаётся привилегированным: этот скрипт не превращает его в безопасный read-only
API. Запускайте под контролируемой операторской учётной записью на машине источника.

Пример закрытого файла `collector.json`:

```json
{
  "docker_host": "unix:///var/run/docker.sock",
  "project": "shop",
  "context": {
    "source_id": "shop-runtime",
    "url": "http://127.0.0.1:3100",
    "service_label": "service_name",
    "services": {"orders": "orders", "payment": "payment"},
    "labels": {"environment": "staging", "project": "shop"},
    "lookback_seconds": 600,
    "assistant_categories": false
  }
}
```

Тот же объект `context` добавьте в профиль RCA; отображение services связывает
кандидата RCA с `com.docker.compose.service`. Project сверяется по
`com.docker.compose.project`. Не включайте пользовательские/секретные значения
в идентификаторы и фиксированные метки Loki. За пределами loopback используйте
HTTPS; bearer token задаётся через `token_env`, не URL или аргументы процесса.

```sh
python3 tools/docker_context_collector.py --config collector.json \
  --database /private/operator-state/shop-events.sqlite --watch
```

Каталог базы создаёт оператор; храните его приватно и постоянно. Новые файлы
создаются с umask 077. SQLite outbox сохраняется до отправки; при неудаче остаётся
для следующей попытки. После сбоя между успешным push и отметкой отправки возможен
повтор, который RCA дедуплицирует. База привязана к настройке; её нельзя молча
переназначить другому проекту. Лимит 10000 записей требует явной архивной ротации,
автоматического удаления истории нет. Оператор наблюдает stderr и организует
запуск/перезапуск службой. Без `--watch` выполняется одна ограниченная итерация.

Наблюдаются start/restart/die/oom/health_status. Только событие `oom` сообщает
об OOM; exit 137 отдельно означает SIGKILL. На свежем start (до 10 с задержки)
сопоставляются image ID и memory limit с ранее наблюдавшимся экземпляром; для
замены нужен единственный предшественник с наблюдавшимся завершением. Несколько
реплик/неполная история не дают надёжного соответствия: изменение не выводится.
Первый запуск не считается развёртыванием; env, файлы конфигурации, feature flags,
факт прохождения CI и git commits не читаются. Это ограниченная история image/
memory-limit изменений, а не универсальная интеграция CI/CD. Лимит памяти —
состояние при чтении inspect (observer.time), не реконструкция всех старых limits.

Loki хранит время Docker события; отдельно передаётся время его наблюдения.
При задержке данные могут появиться только после повторного чтения источников;
старый снимок не меняется. Синхронизация часов, sampling, retention и потери до
установки/при простое неизвестны. Docker сохраняет лишь короткий backlog, поэтому
коллектор не восстанавливает полную историю задним числом. Хранение Loki и его
политику приёма старых записей настраивает оператор.

`lookback_seconds` — 0–600, по умолчанию 0. Предшествующие записи помечаются
«до инцидента»; интервал метрик/трассировок и 62 признака ML не меняются.
Общий бюджет остаётся 100 записей/20 запросов/10 секунд; длинный lookback может
исчерпать выборку, что явно показано как усечение. Исходные поля локальны,
помощнику при отдельном разрешении передаются лишь фиксированные категории,
количества и длительность lookback. Близость события не доказывает причинность.

Основание: [Docker events](https://docs.docker.com/reference/cli/docker/system/events/),
[защита daemon](https://docs.docker.com/engine/security/protect-access/).
