## 1. Суть следующей задачи

Улучшить полезность расследования и проверить, есть ли обоснованный способ
повысить качество ранжирования. Это две отдельные линии с разными результатами:

1. **Расследование/LLM:** помогают ли новые наблюдения правильно различать
   механизмы, проверять альтернативы и выбирать следующий шаг? Не только
   «модель написала красивый JSON со ссылкой».
2. **ML:** какие ошибки связаны с представлением/обучением и устраняет ли их
   один новый challenger на независимых данных? Переобучение входит в план,
   но не является обязательной заменой действующей модели независимо от результата.

Не ставить цель «улучшить любые цифры любой ценой». При отрицательном или
неопределённом результате сохранить действующий продукт и честный вывод.
Масштаб — ВКР, не многолетняя корпоративная RCA-платформа.

## 8. Линия A: помогает ли контекст и LLM

Первое сравнение — один вопрос, не полная факторная матрица.

Предлагается 8 новых случаев: 6 отказов и 2 отрицательных/неполных контроля.
Два режима на **одном и том же** снимке: ML + LLM без новых категорий и
ML + LLM с разрешёнными категориями. Ранг, остальные данные/инструменты,
модель, бюджет и вопрос одинаковы. До отправки зафиксировать состав и случайно
распределить порядок двух режимов. По одному ответу, **не более 16 завершений**,
без повторов ради удачной формулировки. Ошибки и timeout остаются исходами.

Оценивать: механизм, ссылку, действительно ли факт поддерживает утверждение,
альтернативу/опровержение, выполнимость следующего шага, ложное объявление
причины и корректность при неполноте; плюс время/токены/запросы. Сам runner
не присваивает своей прозе итоговую оценку. Reviewer сначала получает ответ
без обозначения режима, затем сверяет с отдельно сохранённой truth/рубрикой.
Разбор одним ИИ раскрывается как ограничение; не называть его независимым
человеческим пилотом или измеренным сокращением MTTR.

После сигнала — отдельное сравнение LLM **без ML-ранга** против LLM с рангом
при одинаковом контексте. Это проверит вклад ранжировщика/эффект привязки.
Не запускать автоматически ещё 16 вызовов: отдельная preregistration и бюджет.
Слепому режиму не передавать ранг через порядок, score, выбор top-k, ID,
ранговые объяснения, filenames и адаптивно отобранные наблюдения.

Измерять полезность детерминированных проверок без LLM как инженерную baseline.
Необходимость LLM ещё предстоит обосновать: наличие категорий может объяснить
весь выигрыш и без генеративной модели. Старый большой INCONCLUSIVE прогон
не продолжать и не пересчитывать его неуспехи как успех нового помощника.

## 9. Линия B: исследование и переобучение ранжировщика

Начать с **одной** проверяемой гипотезы, выбрать по данным, не по модности:

- временная структура/порядок распространения теряется в агрегатах;
- здоровая опора недостаточно покрывает нагрузочные режимы;
- наблюдаемая структура вызовов не отражает исчезнувший/молчащий сервис.

Логи/категории пока не становятся признаками ML автоматически. Нужна отдельная
абляция с проверкой утечки/переносимости. Не начинать GNN, LLM scorer или
ансамбль нескольких новых систем до проверки простой линии.

Минимальные сопоставимые варианты:

1. Frozen champion — действующий продукт, без дообучения.
2. Тот же LambdaMART/схема на новых допустимых train данных — контроль эффекта
   самих данных, если переобучение выполняется.
3. Та же обучающая процедура + **один** выбранный блок изменений. Не приписывать
   эффект признаков одновременно изменившимся данным/гиперпараметрам.

Предлагаемый верхний бюджет: две обучаемые конфигурации, 3 групповых folds,
2 seed для screening (12 ranking fits); после выбора — до 5 финальных fits.
Всего до 17 fits ранжировщика, preprocessing считать/логировать отдельно.
Если групп для честных разбиений не хватает — не заменять их случайными строками;
сократить claim/вернуть INCONCLUSIVE. Гиперпараметрический перебор не нужен.

Сравнение с простой детерминированной эвристикой того же механизма обязательно:
дополнительная сложность ML может оказаться не нужна. Сначала development/OOF,
потом один новый зафиксированный test. Эти 3 folds — только development
screening; его лучший результат не является беспристрастной оценкой выбранной
процедуры. Основная оценка — на отдельном новом test. Если вместо этого
планируется оценивать процедуру вложенным CV, нужен внешний grouped слой
и новый заранее утверждённый бюджет: дополнительные fits не спрятать в «17».

Все обучаемые зависимости (normalization, healthy predictors, selection,
контекстный reranker) обучаются внутри train-разбиений. Действительно frozen
pretrained компонент можно фиксировать лишь при доказанной независимости
его training corpus; оценка тогда явно условна на этот компонент.
Отдельное healthy-only состояние новой целевой системы допустимо как заранее
заявленная калибровка переноса до инцидентов, без fault labels; это не разрешение
фитить baseline по всем test-инцидентам. Его данные и момент фиксации — в ledger.

Primary metric предлагается MRR; AC@1/3/5, candidate coverage, срезы по
механизмам/сервисам и худший срез — обязательные вторичные. Считать полный
знаменатель, парный эффект по одним инцидентам, интервалы по независимым
группам; не выдавать отдельные соседние окна за независимые наблюдения.
Минимальный полезный эффект/неухудшение и runtime limit зарегистрировать до
нового test. «Плюс один удачный случай» не становится автоматически PROMOTED.

## 10. Роли данных и защита от самообмана

M14 — USED_TEST, не train/calibration/свежий test. Его можно описывать как
мотивацию, проверять сохранность старого champion, но не выбирать по нему R3.
Нынешний Loki-пилот — ENGINEERING/USED_DEVELOPMENT, тоже не hidden test.
Ранее прочитанные LLM-случаи не становятся unseen из-за нового имени папки.

В data-ledger нужны source/version/license, роль, дата открытия truth,
system/run/injection-group, повторы, происхождение baseline и feature context.
Соседние/перекрывающиеся окна одного события и повторы механизма — одна группа.
Разделять кампании/системы там, где заявляется соответствующий перенос.
Новый случай на уже известной системе не равен новой независимой системе.

Root/fault/название chaos, команды воздействия, filenames с ответом, сервисная
identity как feature и сведения из postmortem не передаются inference.
Регулярное выражение по одному полю не спасает: controller может записать
истину в error.type или разрешённый текст. Проверять происхождение потока.
Версии/имена можно использовать для routing, не для запоминания теста моделью.

Truth evaluator отделён от collector/scorer. Prediction marker фиксируется
перед открытием нового test; отрицательные/неизвестные исходы сохраняются.
Недостаток observability анализировать отдельно, не исключать ради рейтинга.

## 14. Публичные методические основания

Train/test-разделение должно предшествовать обучаемой подготовке данных;
preprocessing/selection по всем данным искажает оценку.
[scikit-learn: leakage](https://scikit-learn.org/stable/common_pitfalls.html).
Выбор модели и оценку качества разделяют вложенной схемой; группировка
сама по себе не устраняет ошибку выбора по внешнему тесту.
[Nested CV](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html).
В learning-to-rank группа query определяет сравниваемых кандидатов — для нас
это инцидент; конкретные параметры сверять с зафиксированной используемой
версией, не обновлять библиотеку по свежести документации.
[XGBoost Learning to Rank](https://xgboost.readthedocs.io/en/stable/tutorials/learning_to_rank.html).
Источники по расследованию/контексту: `product-research/ITERATION_2_RESEARCH.md`.
