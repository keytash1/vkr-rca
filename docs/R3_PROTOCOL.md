# R3-A: вклад безопасного контекста в помощь расследованию

Регистрация: 19.10.2026, до сбора новых случаев и до LLM-запросов.
Основание запуска: «делай» после `HANDOFF_PRODUCT_NEXT_ITERATION.md`.
Продукт — `rca-workbench` bb910cd653b18d2c5b4f7568d7e1b7fc610a0d58.
Отчёт не редактируется. M13/M14 и их роли данных не меняются.

## Вопрос и границы

Помогают ли категории структурированных журналов предложить конкретную
проверяемую гипотезу механизма при одинаковых остальных наблюдениях и ранге?
Это малый контролируемый development-пилот, не независимая оценка точности,
MTTR, универсального переноса или превосходства LLM над инженером.
Проверка реального Loki уже проведена отдельно; здесь сбор новых записей
непосредственно в учебном HTTP-приложении, без повторной проверки хранилища.

## Данные и сравнение

Одна новая сессия, восемь заранее заданных случаев:

- шесть отказов: 401 и 403 зависимости; два отказа подключения к удерживаемому
  bound, но не listening локальному сокету; два timeout с разными задержками;
- два контроля: здоровый ответ с нерелевантным событием deployment другого
  сервиса; реальные 503, но журнал для помощника недоступен.

По три HTTP-запроса на случай. Симптом, error-флаг и длительности спанов
измеряются приложением; механизм контроллера сохраняется отдельно. CPU/память/
сеть — явно искусственные постоянные фикстуры, не измерения процесса.
Healthy baseline строится на отдельных искусственных здоровых наблюдениях.
Frozen M13 вычисляет новый полный ранг по каждому каноническому входу;
контекст после этого не меняет вход модели и её веса. Это проверка цепочки,
не репрезентативный ML-тест. Контроллер не передаёт тип воздействия ни в
метрики/спаны, ни в вопрос, имена сервисов или идентификаторы фактов.

Пара на каждом случае: C0 — ML + summary LLM без контекста журналов;
C1 — те же ML/факты + штатная enum-only проекция контекста.
В обоих нет дополнительных tools, runbooks или истории диалога. Вопрос один:
«Какие гипотезы стоит проверить, что им противоречит и каких данных не хватает?»
Один штатный prompt `snapshot-report-v7-action-proposals`, одна модель
`gpt-6.1-sol` через уже разрешённое подключение владельца. Модель не меняется
по ходу опыта. Порядок всех 16 задач перемешивается seed 20261019 до ответов.
Перед первым запросом сохраняются входы, hashes и порядок; после — не правятся.

Роли: старые M14 — USED_TEST, прежний Loki-пилот — USED_ENGINEERING;
новые восемь — USED_DEVELOPMENT после этого запуска. Независимого test здесь нет.
Никакие материалы компании, сырые сообщения, URL, credentials, controller truth
или типы Python-исключений провайдеру не отправляются; только разрешённые агрегаты.

## Жёсткий бюджет и остановка

Не более **16 попыток generation API**, включая отказ/неизвестный исход.
Один worker на задачу, `model_calls=1`, без repair/retry; максимум 60 s,
12000 input и 3000 output tokens на ответ по штатному учёту. Удалённый output
limit не обещается: документированный plan-sharing adapter ограничивает ответ
локально; неизвестный удалённый расход сохраняется как неизвестный.
Весь опыт последовательно, максимум 16 минут ожидания workers. Лимит — верхняя
граница, не цель. При auth/quota ошибке либо двух последовательных provider
ошибках остановиться, не менять провайдера и не покупать доступ. При утечке
truth, несовпадении пар или изменении кода — остановка до следующей регистрации.
Возобновление не повторяет ни одну уже начатую задачу (append-only ledger).

## Оценка, до просмотра ответов

Primary: для каждого из шести отказов бинарная оценка — есть ли верная
гипотеза конкретного механизма **с поддерживающим именно её фактом**, а не
общий перечень возможных причин. Предположение без поддержки не успех.
Считать число C1-only выигрышей и C0-only потерь, знаменатель всегда 6;
ошибка/timeout — не успех. Случаи связаны и малы: без significance/CI/MTTR.

Отдельная рубрика: смысловая поддержка ссылок; выполнимая следующая проверка;
альтернатива или явный пробел для неё; необоснованная причинная уверенность;
ложное «здоров» при отсутствии данных; время, usage и неизвестный расход.
Оба контроля не должны превращаться в уверенную причинную историю.
Проверка JSON/ID — только техническая, не смысловая оценка.

Reviewer сначала читает перемешанные ответы с нейтральными ID без arm/truth,
помечает поддержанные/неподдержанные утверждения, затем сверяет с truth.
Один и тот же Codex видит постановку и проводит разбор: это **не независимый
слепой эксперт**. Маскировка облегчает одинаковую рубрику, не устраняет bias.
Генератор не оценивает себя отдельным API-вызовом. Сохраняются пояснения каждого
вердикта, чтобы человек мог пересмотреть. Дополнительно сопоставить штатные
детерминированные проверки UI с теми же категориями без LLM.

## Решение

Минимальный сигнал для сохранения категории как полезного необязательного
входа помощника: C1-only минус C0-only >= 2 из 6; не менее 14/16 валидных
ответов; оба C1-контроля корректны; нет критической утечки/уверенной выдуманной
причины в C1. Иначе INCONCLUSIVE/REJECTED для заявленного эффекта, без поиска
удачного повтора. Никакой смены ML на основании этого опыта.
Если детерминированная проверка уже даёт тот же следующий шаг, явно признать:
выигрыш относится к данным; дополнительная польза LLM ещё не установлена.
Конкретный дефект безопасности/толкования исправляется адресно с локальной
регрессией; изменённый prompt не прогоняется повторно на этих же случаях
под именем нового скрытого результата.

Основание методики: task-specific paired eval, заранее выбранные критерии,
полный учёт отказов и семантический разбор вместо оценки «красивый ответ» —
[OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).
Новый ML-challenger и LLM без подсказки ранга остаются отдельными будущими
протоколами, не автоматическим продолжением ещё на десятки запросов.
